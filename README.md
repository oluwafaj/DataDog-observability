# Datadog monitoring for Faj Azure infrastructure

This is a **separate Terraform root module** for Datadog configuration. Keep it separate from the Azure resource deployment so the Datadog provider credentials and lifecycle do not become coupled to Azure resource provisioning.

## What it covers

The Datadog Azure integration discovers supported Azure resources in the subscription(s) accessible to its Entra application, including the project's:
- Virtual machines
- App Services and App Service Plans
- Storage accounts
- Key Vault
- Virtual networks and network security groups (resource metadata/inventory)
- Log Analytics workspace and Azure Monitor resources
- Microsoft Defender for Cloud configuration (where exposed by Azure integration/resource collection)

The integration enables Azure metrics and resource collection. It does **not** mean every resource has a continuously emitted metric. For example, resource groups, VNets, and NSGs are primarily configuration/inventory objects; use Azure Activity Logs, Azure Resource Health, CSPM/security posture, and log forwarding for operational/security signals.

Included monitor:
- Azure VM CPU high (`azure.vm.percentage_cpu`).

Optional App Service 5xx monitor:
- Disabled by default. Confirm the exact metric name and dimensions for your App Service in Datadog Metrics Explorer before enabling. Azure metric availability depends on the resource type and configuration.

## Prerequisites

1. A Datadog organization and permission to create integrations and monitors.
2. Datadog API key and Application key with suitable permissions.
3. An Entra ID app registration for Datadog with `Monitoring Reader` on every Azure subscription to be monitored. Datadog recommends secretless/federated authentication for production. This starter uses a client secret for the simplest first setup; replace with the secretless configuration generated by your Datadog Azure integration setup if possible.
4. Terraform >= 1.5 and network access to the Terraform Registry and Datadog API.

## Step 1 — Set Datadog credentials in your shell

Do not put Datadog API/App keys in `.tfvars`, source control, or Terraform code.

For macOS zsh, in the terminal:

```bash
export DD_API_KEY="YOUR_DATADOG_API_KEY"
export DD_APP_KEY="YOUR_DATADOG_APPLICATION_KEY"
```

For production, use your CI/CD secret store (GitHub Actions secrets, Azure Key Vault, or an approved secret manager) rather than shell history.

## Step 2 — Configure Azure integration credentials

The Entra app registration must have `Monitoring Reader` at the subscription scope. Use the tenant ID and application/client ID in `terraform.tfvars`.

For a first lab run, export the Azure client secret as a Terraform input:

```bash
export TF_VAR_azure_client_secret="YOUR_AZURE_APP_CLIENT_SECRET"
```

Copy the example variables file:

```bash
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars` and replace the tenant/client IDs and environment/team values. Keep `azure_client_secret` out of that file; it is supplied through `TF_VAR_azure_client_secret`.

**Enterprise recommendation:** use Datadog's Secretless Auth/federated workload identity instead of a long-lived client secret. In Datadog, go to Integrations → Microsoft Azure → Add App Registration → Terraform, choose Secretless Auth, and use the generated Terraform configuration and federation details. The exact trust configuration is organization-specific.

## Step 3 — Initialise and review

```bash
terraform init
terraform fmt -recursive
terraform validate
terraform plan
```

Review the plan. Applying this configuration creates/updates a Datadog Azure integration and Datadog monitors; it does not create Azure infrastructure.

## Step 4 — Apply

```bash
terraform apply
```

Allow up to around 10 minutes for Azure metrics/resource metadata to begin appearing. Check Datadog Infrastructure, Metrics Explorer, and the Azure integration tile.

## Step 5 — Confirm metric names before enabling more monitors

In Datadog → Metrics → Explorer:
- Search `azure.vm.percentage_cpu`.
- Filter by `subscription_name`, `resource_group`, `name`, or `host`.
- Confirm the metric is populated for the VM.
- For App Service, search `azure.app_services.*` and confirm the exact HTTP error metric and available tags before setting `enable_app_service_5xx_monitor = true`.

If a metric is missing, verify the Azure app's `Monitoring Reader` permission, that the resource is running where applicable, and that the relevant Azure metrics/diagnostics are enabled.

## Enterprise operating standards to add before production

- Use Secretless Auth / OIDC federation; do not commit secrets.
- Store Terraform state remotely in an Azure Storage account with encryption, versioning, locking/lease controls, and restricted RBAC. Do not use local state for shared production work.
- Run `terraform plan` in pull requests and require approval before apply.
- Use separate state and Datadog `env` tags for Dev, QA, and Production.
- Set monitor ownership (`team`), environment, service, severity/priority, runbook links, and actionable notification targets.
- Route production critical alerts to PagerDuty/incident management and lower-severity alerts to the team's chat channel.
- Tune thresholds against observed baselines to avoid alert fatigue.
- Add log pipelines, Azure Activity Log forwarding, Azure Resource Health and Defender/CSPM signals as separate workstreams; metric monitors alone do not cover every resource/security event.
- Review Datadog host billing: Azure VM integration can count monitored VMs as billable hosts.

## Suggested deployment per environment

Use this directory as a separate root. For each environment, use a separate backend key/state and a separate `terraform.tfvars` (kept out of Git), or a workspace only if that matches your organisation's state policy. Do not share a single state between Dev, QA, and Production.
